# UI integration contract

Base URL: `http://127.0.0.1:8000`. There are no application frontend assets. `/docs` is autogenerated API documentation. The complete input schemas and response operations are in [openapi.json](openapi.json).

## Authentication and tenancy

Send `Authorization: Bearer <backend-identity-token>`. The configured token selects both tenant and role. The backend does not accept a graph name or tenant override from a request. Tokens are generated privately in `.env` by `scripts/init_env.py`; obtain the appropriate scoped token from the backend owner. OpenAI/provider keys never belong in the UI.

Roles: operator admits evidence, corrects memory, approves effects, and starts agents; planner controls planner runs; executor controls executor runs; viewer can inspect tenant-local state. Viewer has no mutation permission. A role cannot control a different agent role's run. The operator can drive either role.

CORS permits only configured origins. Defaults are `http://localhost:3000` and `http://localhost:5173`. Change `REWIND_CORS_ORIGINS` to your UI URLs and restart. A public UI should obtain a scoped user token at runtime rather than bundling a real operator credential.

## Read endpoints

| Method/path | Purpose |
| --- | --- |
| `GET /health` | Database/module health and whether a live model is configured |
| `GET /ready` | 200 when configured tenants are ready; 503 while unavailable/repairing |
| `GET /api/me` | Tenant, role, pseudonymous actor ID |
| `GET /api/state` | Tenant state, event sequence, record counts, model readiness |
| `GET /api/graph?include_episodes=false&limit=1000` | Nodes and edges for your renderer; includes truncation flag |
| `GET /api/events?after=0&limit=200` | Ordered audit events, next cursor, latest sequence, has-more flag |
| `GET /api/sources` | Source versions and their status/authority/content/hash |
| `GET /api/memory?subject=northstar&usable_only=true` | Current grounded memory, status, revision, and retained history if requested |
| `GET /api/memory/{id}/provenance` | Grounding verdict, valid justification IDs, original evidence nodes, relationships |
| `GET /api/tasks`, `/api/runs`, `/api/actions`, `/api/repairs`, `/api/receipts` | Paginated collections using `offset` and `limit` |
| `GET /api/records/{id}` | A single record within the authenticated tenant |
| `GET /api/runs/{id}/episodes` | Persisted conversation/tool history, ordered by creation time |
| `GET /api/tools?role=planner` | Tool descriptions and JSON argument schemas for the authorized role |

Paginated collections return `{items, total, next_offset}`. Memory returns `{items, mode}`. Events return `{items, next_cursor, latest_sequence, has_more}`. Poll events approximately every 500–1000 ms; after a refresh use the saved cursor. On a reconnect, refresh graph/state as necessary. Do not use UI animation to infer a committed effect.

Graph nodes are flat record objects with `id`, `kind_label`, `created_at`, and type-specific fields. Memory also has `kind` (`semantic`, `plan`, `procedural`). Edges are `{source, type, target, data}`. Stable renderer edge IDs can be formed from the source/type/target triple. Backend graph data does not depend on a specific frontend library.

Statuses should be labeled, not inferred from color. Memory is `candidate`, `active`, `unsupported`, or `superseded`; sources are `active`/`revoked`; runs are `queued`, `running`, `completed`, `awaiting_approval`, `awaiting_input`, `failed`, `interrupted`, or `restart_required`; actions are `pending`, `approved`, `stale`, or `committed`. Repair mode pauses usable retrieval and effect execution. Graph/audit inspection remains possible.

`GET /api/memory?usable_only=true` returns 503 `REPAIR_IN_PROGRESS` while a tenant is paused. The unfiltered memory endpoint remains available for inspecting repair history.

## Operator endpoints

| Method/path | Input/result |
| --- | --- |
| `POST /api/sources` | SourceCreate; new immutable admitted source |
| `POST /api/memory` | MemoryCreate; operator-admitted typed memory |
| `POST /api/memory/{id}/supports` | `{inputs:[source_or_memory_ids]}`; add an alternative complete justification |
| `POST /api/memory/{id}/review` | Admit an agent's candidate after operator review |
| `POST /api/sources/{id}/revocation-preview` | Preview candidate descendants/retained memories; no mutation |
| `POST /api/sources/{id}/revoke` | `{reason,idempotency_key}`; persisted repair and report |
| `POST /api/corrections` | New source + semantic fact + optional superseded memory, committed together |
| `POST /api/repairs/recover` | Recover an interrupted repair when no local agent is active |
| `POST /api/tasks` | TaskCreate with supplier/invoice IDs, goal, constraints |
| `POST /api/actions/{id}/approve` | `{payload_hash}` from the exact inspected proposal |
| `POST /api/actions/{id}/learn-procedure` | Learn a procedure from a committed, unrecalled effect and its receipt |
| `POST /api/demo/seed` | Demo-only setup/reset; operator only |

For revoked/unsupported memory use a new correction version rather than attaching evidence to revive its old ID. A correction with `supersedes_id` must address the same subject/predicate, and the old memory must first lose usable support through repair. Whole-source evidence spans and canonical-content hashes are persisted in justifications. Operators, not the agent, decide admission/authority.

## Run endpoints

`POST /api/tasks/{task_id}/runs` with `{role:"planner"|"executor",mode:"live"|"scripted"}` returns **202** with the queued Run. A background job starts asynchronously. Poll the Run record/events. Planner saves a supported plan and hands off the Task; only then start an executor. The executor has a new context and retrieves shared graph memory independently.

Live transport is server-configured: `AGENT_PROVIDER=codex_cli` uses the host's signed-in Codex CLI without a model API key; `openai` uses the compatible API adapter. `/health` and `/api/state` expose `agent_provider`; Run records persist `provider`, `model`, and usage totals. For Codex, `model_configured` means an executable is available, not a guaranteed usable login/quota. CLI login and actual decision failures appear in the Run. No UI change or Codex credential is required.

`POST /api/runs/{run_id}/continue` resumes an approval-paused executor after its Action is approved. A repaired/interrupted/failed run cannot be continued using its old context: create a fresh run for the Task's current owner role and generation. A completed Task cannot be paid again. A committed invoice under another Task is also blocked.

`POST /api/runs/{run_id}/tools` with `{name,arguments}` exposes the same role-scoped tools used by the internal agents. The backend binds run/tenant/role; callers cannot override them in tool arguments. Planner can propose an unadmitted semantic fact with `propose_memory`; review is a separate operator endpoint. Executor can propose/execute only supported effects. Approvals and source revocation are not agent tools.

`POST /api/actions` accepts `{run_id,payload,idempotency_key}` for an executor. The server resolves all required facts and requires current reads by that run. `POST /api/actions/{id}/execute` attempts the code-enforced gate; returns `{receipt,already_committed}` when successful. Retrying a committed action returns its original receipt without another effect.

## Exact demo sequence

1. `POST /api/demo/seed` with `{}`. For an existing demo use `{reset:true,confirm:"reset-this-demo-tenant"}`; reset fails if agents are active or the tenant is not marked as a demo.
2. Start planner for `task-invoice-1042`; wait for `completed` and Task `handed_off`.
3. Start executor; wait for `awaiting_approval`; find its action by `run_id`.
4. Inspect the action/provenance and approve its exact payload hash. Do not continue yet.
5. Preview and revoke `src-onboarding-incorrect`, with a reason and fresh idempotency key.
6. Try executing the old action. Show the **409 `STALE_ACTION`** rejection and absence of an old receipt.
7. Inspect repair report: routing/derived plans lose support; supplier name retains purchase-order support; unrelated invoice/terms survive.
8. Submit the reviewed correction below.
9. Start a fresh planner, then fresh executor, following current Task generation.
10. Approve the new action; continue the executor; wait for `completed` and `receipt_verified:true`.
11. Inspect the receipt and learn a verified procedure if desired.

```json
{
  "source": {
    "id": "src-routing-correction-reviewed",
    "title": "Reviewed supplier correction",
    "content": "Fictional supplier confirms BANK-DEMO-CORRECT.",
    "authority": "authoritative"
  },
  "memory": {
    "id": "mem-routing-correct",
    "kind": "semantic",
    "subject": "northstar",
    "predicate": "payment_routing",
    "value": "BANK-DEMO-CORRECT",
    "inputs": ["$source"]
  },
  "supersedes_id": "mem-routing-wrong"
}
```

For corrections only, the backend replaces `memory.inputs` with the ID of the newly admitted source. `$source` is a documented placeholder, not an arbitrary provenance bypass.

Repair report fields: `invalidated`, `preserved`, `affected_runs`, `stale_actions`, `review_needed`, and `resumable_tasks`. All are actual record IDs. `preserved` means alternative support survived; its evidence revision can still change. Completed historical receipts remain and are review-needed rather than reversed.

## Errors

Domain errors return `{error:{code,message,details}}`. Malformed contracts return FastAPI's 422 validation `detail` list. HTTP 401 means invalid/missing identity; 403 means a role/scope denial; 404 means not found within this tenant; 409 means a state/provenance conflict; 503 means unavailable database/model/repair state.

Useful codes: `STALE_ACTION`, `STALE_MEMORY`, `STALE_RUN`, `MISSING_APPROVAL`, `INVALID_PROVENANCE`, `CONFLICTING_FACT`, `PAYLOAD_MISMATCH`, `REPAIR_IN_PROGRESS`, `IDEMPOTENCY_CONFLICT`, `INVOICE_ALREADY_PAID`, `MODEL_NOT_CONFIGURED`, `DATABASE_UNAVAILABLE`, `REPAIR_REQUIRED`, and `RESET_CONFIRMATION_REQUIRED`.

On stale state, refresh Task/memory and create a fresh run. Do not blindly retry the same old proposal. On ambiguous receipt responses, query `/api/records/{action_id}` or retry the same approved action ID. Do not invent a new idempotency key for the same effect.
